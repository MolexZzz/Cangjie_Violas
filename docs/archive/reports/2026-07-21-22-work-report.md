# 历史报告：Violas 仓颉复现阶段工作

> 本文保留实验演进过程；发布结论以 `docs/experiments.md` 和 `results-summary/` 为准。

## 一、本阶段具体任务

本阶段围绕 Violas Python 论文版本在仓颉环境下的复现，实际完成了以下三项工作：

1. **生成一套供所有实现共同读取的固定实验输入。** 使用 Python 论文代码规定的 CLIP `ViT-B/32` 模型，将三套原始图片转换为 512 维向量，并固定每张图片的 `recordId`、90% 建库数据、10% 查询池、每个数据集的 200 个查询及其 ground truth。仓颉 Violas、Milvus、Qdrant 和 Chroma 均读取同一份结果，避免因图片向量、数据划分或正确答案不同而造成不可比。
2. **补齐仓颉侧可重复执行实验所需的代码。** 修改 HDMG 的索引状态管理、参数检查和构图内存实现；增加非交互式批量测试、实时进度、断点续跑和结果文件保存；接入 Milvus、Qdrant、Chroma，同时保存数据库直接向量 Top-3（论文基线口径）和“召回 30 个候选后按 mixed score 重排”（扩展实验）两套结果。
3. **完成三个图像数据集的第一轮完整规模测试。** Caltech-101 使用 8,677 条记录、CUB-200-2011 使用 11,788 条记录、COCO 使用 10,000 条记录；分别用完整的 90% 训练部分建库，在固定的 200 个查询上测试 β=0.0～1.0 的 11 组参数，同时运行仓颉 HDMG、两种无图代表向量搜索，以及 Milvus、Qdrant 和 Chroma。论文 `w/o HDMG` 和 graded NDCG 已在后续审计中补齐，但下面引用的首轮数值仍是旧协议结果，需要重新运行后替换。

Python 代码保持不变，作为参考实现；本阶段只修改仓颉实现及实验工具，并让各系统在相同输入和参数下运行。

## 二、主要完成工作

### 1. 建立与 Python 对齐的图像数据预处理协议

根据 Python 图像 Benchmark 的实际处理逻辑，建立了 `python-paper-90-10` 冻结实验协议。三个数据集统一使用：

- CLIP `ViT-B/32` 生成 512 维图片向量；
- 文本模板 `a photo of a {类别名}` 生成类别 key vector；
- 按类别进行 90%/10% 训练—测试划分；
- `random_state=42`；
- 每个数据集选择 200 个查询；
- `topK=3`；
- β 从 0.0 到 1.0，步长为 0.1；
- KMeans 微簇参数 `alpha=0.5`；
- 为每条数据生成稳定 `recordId`，并保存数据哈希、模型哈希、划分和预处理配置。

当前冻结数据规模如下：

| 数据集 | 完整记录数 | 建库向量数 | 10% 查询池 | 本轮查询数 | 类别数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Caltech-101 | 8,677 | 7,766 | 911 | 200 | 101 |
| CUB-200-2011 | 11,788 | 10,597 | 1,191 | 200 | 200 |
| COCO-10k | 10,000 | 8,967 | 1,033 | 200 | 80 |

这里的“全量实验”表示使用完整训练部分建立索引，并按照 Python Benchmark 默认上限执行 200 个冻结查询，而不是只使用此前仓库中的 20 条或少量样例。

### 2. 完善仓颉侧 HDMG 与无图消融实验

对仓颉侧 HDMG 构建、检索和索引生命周期进行了补充与优化：

- 增加索引构建状态、数据版本和数据变更后的失效规则；
- 增加参数边界检查、未构建时的 fallback 和稳定排序；
- 将 HDMG 配置、评分和统计逻辑进一步模块化；
- 去除构图阶段完整的组间距离矩阵，将额外距离内存由 `O(G²)` 降为单节点候选所需的 `O(G)`；
- 保留构图计算量 `O(G²)`，后续继续针对更大规模数据 profiling；
- 新增 entry、walk、rerank、候选池、跳数和构建时间统计；
- 按论文定义补充 `w/o HDMG`：先按 entity score 路由 5 个 entity group，再在每个已路由 group 内直接扫描微簇、保留最多 9 个微簇，最后按 mixed score 重排成员；不再把全局代表向量扫描误标为论文消融。

通过对冻结向量统一归一化、使用 `1-dot` 快速余弦距离以及启用仓颉 `-O2` 编译优化，HDMG 查询和构建性能得到明显改善。在 Caltech 同一索引上的对照中：

- HDMG 平均查询时间由约 76.50 ms 降至约 1.25 ms；
- HDMG 构建时间由约 77.6 s 降至约 0.91 s；
- 优化前后已测 Recall 结果保持一致。

### 3. 完善非交互 Benchmark 与结果持久化

原 Benchmark 依赖交互输入，难以批量执行和保存结果。本阶段完成了：

- 单数据集、指定查询数和指定 β/全 β 的命令行入口；
- 每个查询的实时进度显示；
- Caltech、CUB、COCO 分数据集独立运行；
- `-Resume` 断点续跑；
- Recall@3、NDCG@3 和平均查询延迟统计；
- 仓颉 HDMG、RepScan-9、Representative-3 和 PythonFlat 的统一输出；
- 实验日志、结构化 JSON 和最终 Markdown 表格持久化；
- 旧协议结果检测，避免把缺少新字段的缓存误认为已完成实验。

### 4. 接入 Milvus、Qdrant 和 Chroma

仓颉侧通过统一的进程协议调用 Python 数据库适配器，完成了三个数据库的真实服务接入。数据库实验与 Python Mixed Search 的流程对齐：

1. 使用图片向量从数据库召回 `topK × 10=30` 个候选；
2. 对候选计算
   `mixed_score = β × semantic_distance + (1-β) × embedding_distance`；
3. 按 mixed score 重排并选择 top-3；
4. 与当前 β 对应的冻结 mixed ground truth 比较；
5. 统计 Recall@3、NDCG@3，以及“数据库候选召回 + 本地重排”的总延迟。

后续复核确认，论文主表中的数据库结果应使用两阶段流程：数据库按 embedding 召回 30 个候选，再由 Benchmark 在本地按 mixed score 重排。协议因此升级为 `violas-paper-table2-v5`。

- `paperComparison.method=vector-candidate-plus-local-mixed-rerank`，候选数为 30；
- 按 exact mixed target 计算 Mixed Recall@3；
- 按论文 Equation 14 计算 graded Mixed NDCG@3；
- 延迟包含数据库候选召回和本地 mixed 重排；
- `rawComparison` 另行保存数据库直接 Top-3，仅作为辅助诊断。

其中两阶段 mixed 重排对应论文 Table 2；raw Top-3 不进入论文主表。

### 5. 修复 β=1.0 的同分结果校验问题

当 β=1.0 时，评分完全由类别文本向量决定，同一类别下多张图片会得到完全相同的分数。Python 和仓颉可能从同一类别中选出不同的三张图片；图片 ID 不同，但语义检索结果等价。

原实现仍要求冻结 ground truth 与仓颉结果的图片 ID 完全一致，导致 CUB 在 β=1.0 时错误中断。本阶段将该边界情况改为与 Python Benchmark 一致的类别 key 级校验，并使用 CUB 全部 200 个查询验证通过。

## 三、实验完成情况

三个图像数据集均已完成：

- 仓颉 Violas/HDMG：200 查询 × 11 个 β；
- 旧结果中的两种无图代表向量搜索已完成 200 查询 × 11 个 β；论文定义的 `w/o HDMG` 已在代码中补齐，正式数值需使用新版协议重新运行；
- Milvus、Qdrant、Chroma：每个数据库均完成 200 查询 × 11 个 β；
- 三个数据库、三个数据集共完成 19,800 次两阶段 mixed query-beta 评测；
- 所有正式数据库结果均通过 schema v2、协议 v3、11 个 β、200 查询和候选池 30 的完整性检查。

### 三图像数据集平均结果（β=0.5）

| 方法 | Mixed Recall@3 | Mixed NDCG@3 | 平均延迟（ms/query） |
| --- | ---: | ---: | ---: |
| Violas（仓颉 HDMG） | 0.998 | 0.999 | 0.87 |
| RepScan-9（非论文 w/o HDMG） | 0.999 | 0.999 | 3.26 |
| Milvus Mixed | 0.948 | 0.956 | 7.04 |
| Qdrant Mixed | 0.956 | 0.961 | 18.95 |
| Chroma Mixed | 0.956 | 0.961 | 8.99 |

结果表明，在 β=0.5 的平衡混合检索场景下，仓颉 Violas 的 Recall@3 和 NDCG@3 均接近 1.0，并且查询延迟低于无图消融方法和三个外部数据库。

仓颉结果与 Python 仓库公开的三个图像数据集结果也较为接近。例如 β=0.5 时：

| 数据集 | 当前仓颉 Violas Recall@3 | Python 公开结果 |
| --- | ---: | ---: |
| Caltech-101 | 0.9983 | 0.9985 |
| CUB-200-2011 | 1.0000 | 1.0000 |
| COCO | 0.9967 | 0.9965 |

## 四、当前结论

1. 三个图像完整数据集已经能够使用同一冻结输入在仓颉、Milvus、Qdrant 和 Chroma 上运行，基本解决了早期“小样例可运行但无法正式对比”的问题。
2. 仓颉 Violas 在 β≥0.4 时已经表现出较高的 Mixed Recall@3 和 NDCG@3，β=0.5 的结果与 Python 公开图像结果接近。
3. HDMG 查询速度显著优于当前全局代表向量扫描方法，说明图索引确实缩小了候选搜索范围；论文定义的 `w/o HDMG` 已实现，正式结论需用新版协议复测后给出。
4. 数据库两阶段 mixed 检索、计时和结果字段已经明确，能够从原始 JSON 追溯到最终 Markdown，不再依赖含义模糊的表头解释。
5. 当前三图像数据集平均结果只能作为图像侧阶段性结果，不能直接等同于论文 Table 2 的六数据集平均结果。

## 五、仍需解决的问题

1. 在 β=0.0～0.3 的低语义权重区间，部分数据集上 HDMG Recall 低于当前无图扫描方法，说明图遍历仍存在少量候选遗漏，需要调整候选池、入口选择和遍历参数。
2. Milvus、Qdrant、Chroma 目前运行在 Docker 服务中；尤其 Chroma 的 HTTP 服务方式与 Python 参考代码的本地嵌入式方式不同，因此延迟只能作为当前统一环境下的横向对比，不能直接解释为数据库官方性能。
3. 已将 NDCG 改为论文公式中的 graded NDCG，即以 mixed score 计算 `2^score-1` 增益；旧结果仍是二元 NDCG，必须通过新版协议重新运行，不能混用。
4. 当前只完成三个图像数据集；论文 Table 2 的六数据集平均值还需要合并三个文本数据集结果。
5. 尚未统一完成重复运行、预热次数、P50/P95、峰值内存和索引大小统计。
6. HDMG 构图虽然降低了额外内存，但 `O(G²)` 计算量仍需继续 profiling 和优化。

## 六、下一阶段计划

1. 针对 Caltech、CUB 和 COCO 的低 β 区间进行 HDMG 参数调优，在保持低延迟的同时缩小与 `w/o HDMG` 的 Recall 差距。
2. 对关键参数进行控制变量实验，包括候选池倍数、最大遍历步数、入口阈值和邻居数量，并保存准确率—延迟折中曲线。
3. 增加预热和多次重复运行，补充 mean、P50/P95、峰值内存和索引大小。
4. 与文本数据集负责人统一结果协议，最终生成六数据集平均表。
5. 统计仓颉核心代码行数，并进一步明确与 Faiss 的比较口径：Faiss 作为向量索引基线，比较检索准确率、查询延迟、构建时间、内存和索引大小，而不是简单比较功能是否完全相同。
6. 在核心复现和性能调优完成后，再根据时间补充 dependency、multimodal、contextual vector 等上层接口。
