# 科研实践工作日志

日期：2026 年 7 月 28 日

## 本次工作

本次工作对科研实践前两个阶段进行收尾。第一阶段完成 Violas 仓颉实现的代码审查、架构整理
以及与 Faiss 的代码量对比；第二阶段完成三个图像数据集的完整查询集实验，并确定当前
HDMG 默认参数。全量实验的执行过程已记录在前期日志中，本次只汇总最终结果和阶段结论。

### 1. 代码审查与架构整理

本次审查以 `cj_core/src/` 为范围，重点检查了数据组织、索引配置、对象维护和测试覆盖情况。
当前实现以 `VectorMap` 为统一入口：`VectorGroup` 保存代表向量、实例向量及描述信息，
`clustering` 负责微簇划分，`hdmg` 负责图索引配置，`mixed_scoring` 负责语义距离与
embedding 距离的组合，`bench` 则实现实验输入和指标统计。

在原有实现基础上，主要完成了以下整理：

1. 将 HDMG 构建参数和查询参数分别收敛到 `HdmgBuildConfig` 与 `HdmgSearchConfig`，
   避免实验参数散落在检索流程中，并为后续参数扫描保留统一入口。
2. 明确对象数据与派生索引的生命周期。插入、更新、删除对象或修改 key vector 后递增
   数据版本并使当前 HDMG 失效；查询发现索引缺失或过期时，使用精确候选路径并记录回退状态。
3. 增加向量维度和配置参数校验，避免不一致向量或非法候选参数进入构图与查询阶段。
4. 补充 mixed score、向量运算、`VectorGroup` 增删改、维度校验、HDMG 失效与重建、
   稳定排序和非法配置等测试。当前仓颉工程共有 9 项单元测试，均已通过。
5. 整理工程目录与公开接口说明，将核心实现、实验工具和结果汇总分开，减少实验代码与
   存储核心之间的耦合。

审查中仍发现一项需要后续处理的问题：`VectorMap` 同时承担数据容器、关系管理、索引状态和
检索入口等职责。若继续增加代码项目检索等应用，宜将索引生命周期和关系存储逐步拆分为
独立组件，而不是继续扩大 `VectorMap`。

### 2. 与 Faiss 的代码量对比

统计采用统一的 source LOC 口径：计算非空且去除纯注释后的源码行，不计入文档、数据、
构建产物和实验输出。仓颉数据来自当前仓库；Faiss 数据对应 commit
`7d4bb39f7eb3e9bb4d160aa38ec821ee1a407afc`。
仓颉统计固定于第三阶段代码加入前的 commit
`240f994b7f42fbf232c67daf881389f5030d9300`，因此不包含后续代码检索案例入口。

整体工程规模如下：

| 统计范围 | 文件数 | 源码行数 |
| --- | ---: | ---: |
| 仓颉 Violas 全部生产代码 | 14 | 4,504 |
| 仓颉 Violas 存储核心 | 6 | 1,964 |
| Faiss CPU Library | — | 95,298 |
| Faiss CPU 与 GPU 代码 | — | 132,769 |

由于 Violas 与 Faiss 的工程定位差异较大，又对本实验实际涉及的主要索引模块作了单独统计：

| 实现 | 主实现文件数 | 主实现源码行 |
| --- | ---: | ---: |
| 仓颉 Violas HDMG/Mixed Search | 3 | 1,453 |
| Faiss IndexFlatIP | 4 | 1,204 |
| Faiss IndexIVFFlat | 4 | 1,980 |
| Faiss IndexHNSWFlat | 4 | 2,680 |

结果表明，仓颉 Violas 的完整工程规模远小于 Faiss，但 HDMG/Mixed Search 主体与 Faiss
单个索引实现处于相近数量级：代码量高于 `IndexFlatIP`，低于 `IndexIVFFlat` 和
`IndexHNSWFlat`。

该对比只用于说明实现范围，不能直接解释为算法复杂度或代码质量差异。Faiss 还包含公共索引
接口、量化、SIMD、GPU 和平台适配代码；表中的单索引统计未重复计入这些共享模块。
同时，Faiss 使用 C++ 头文件与实现文件分离，仓颉没有相同的组织方式。两者的检索目标也不同：
Faiss 基线计算 embedding 相似度，Violas 计算语义距离与 embedding 距离的混合结果。

### 3. 全量实验与参数调优收尾

第二阶段使用 Caltech-101、CUB-200-2011 和 COCO 三个图像数据集。图片和类别文本均使用
CLIP ViT-B/32 编码为 512 维向量，并按类别划分 90% 建库数据和 10% 查询数据。三个数据集
均使用完整的 10% 查询集，不再采用前期的小批量查询。

β=0.5 时的仓颉 Violas 结果如下：

| 数据集 | 建库向量 | 查询向量 | Recall@3 | NDCG@3 | 延迟（ms/query） |
| --- | ---: | ---: | ---: | ---: | ---: |
| Caltech-101 | 7,766 | 911 | 0.998536 | 0.999994 | 1.085818 |
| CUB-200-2011 | 10,597 | 1,191 | 1.000000 | 1.000000 | 1.421441 |
| COCO | 8,967 | 1,033 | 0.996450 | 0.999944 | 0.904350 |
| 三数据集平均 | — | — | 0.998329 | 0.999979 | 1.137203 |

在完整数据实验基础上，又使用每个数据集固定的前 200 个查询比较了五组 HDMG 参数。
`wide-candidate-pool` 的平均 Recall@3 最高，为 0.999444，但平均查询延迟较
`paper-default` 增加约 37%；`small-candidate-pool` 的延迟最低，但 COCO Recall@3
下降至 0.991667。综合准确率、延迟和跨数据集稳定性，当前实现继续采用
`paper-default`。

本阶段同时固定了实验输入哈希、运行参数、结果 JSON 和汇总表，并通过仓颉构建、9 项单元测试
及结果文件校验。由此确认当前实现已经从基本功能和小批量验证推进到完整查询集实验，第二阶段
目标已完成。
