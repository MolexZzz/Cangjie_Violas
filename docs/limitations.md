# 已知限制

## 实现

核心向量以 `Float64` 保存，内存开销高于常见的 Float32 向量库。HDMG 构图需要计算微簇间的
成对距离，复杂度为 `O(G²)`，且当前版本尚未实现索引序列化。`rep` 和 `single` 接口保存的是
精确遍历统计，并非独立 ANN 索引。

`VectorMap` 目前同时承担存储、索引状态和检索入口等职责。部分容器为兼容旧接口而保持公开，
调用方直接修改这些容器后必须调用 `markDirty()`。

## 实验

结果只覆盖三个图像数据集，其中 COCO 使用预先确定的 10,000 张图片，并非 COCO 全集。
外部数据库通过 Python SDK 适配器访问，不是仓颉原生客户端；Docker service 模式下测得的
延迟包含通信开销。参数扫描使用每个数据集前 200 个查询，默认配置另有完整查询集结果。
所有延迟数据只适用于本次运行环境。

Faiss 基线负责 embedding 向量检索，Violas 负责语义与 embedding 的混合检索。两者采用的
真值和目标函数不同，Recall、NDCG 与延迟不能直接用于排名。代码行数只反映选定模块的规模，
不代表算法复杂度或代码质量。

## 后续工作

后续工作主要包括拆分 `VectorMap` 的索引职责、增加 HDMG 序列化和增量更新、评估连续
Float32 存储，以及使用 block kNN 或近似方法降低构图成本。若扩展实验，应优先补充文本
数据集，并在统一运行环境中重新测量外部数据库延迟。
